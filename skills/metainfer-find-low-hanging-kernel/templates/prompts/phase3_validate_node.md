# Phase 3 — Per-node validator prompt

(This file is reference documentation for how `scripts/validate_graph.py`
constructs per-node prompts. The actual prompts are generated by the script
from this template — see `emit_prompts()` in the script.)

## Why per-node

The whole graph is too big to feed to an LLM at once — the model will
hallucinate and miss real inconsistencies. The script generates one prompt per
node, containing only:

1. That node's JSON.
2. The JSON of its immediate predecessor and successor nodes (not the whole graph).
3. Pointers to the read-only Phase 1 / Phase 2 memory files and the framework source tree.

The model must return strict JSON:

```json
{"verdict": "ok" | "fix", "reason": "<short>", "proposed_patch": {"<field>": <new_value>}}
```

## What the model checks, per node

- Does the stated `operator` and `step_purpose` match the code at
  `framework_file:line` and at the `call_site` entry of `framework_refs`?
- For every entry in `framework_refs`, open the cited `file` at the cited
  `line` (±~20 lines of context) and verify the cited code actually matches
  what the `role` and `note` claim. Mismatched role, wrong line, or content
  that contradicts the `note` → `verdict: fix` with a `proposed_patch` that
  corrects the offending `framework_refs[i]` entry. (The script's structural
  check has already verified each `file` exists on disk when `framework_src`
  was provided, so the model focuses on semantic fit, not file existence.)
- Do the input/output `shape`s and `dtype`s match the framework's expectation
  at that call site (cross-check Phase 1)?
- **Are the shapes per-rank-correct under TP?** If Phase 2 says TP>1, the node
  must use per-rank dim vars consistent with the per-weight TP policy.
- Does the `perf` data line up with Phase 2 for the cited `source_kernel_ids`
  (mean within a sane tolerance, call count plausible)?

## How the orchestrator runs it

Two supported execution paths:

1. **`validate_graph.py --mode claude-cli`** — the script itself shells out to
   `claude -p` per node in parallel (workers default 4). Self-contained.
2. **`validate_graph.py --mode emit-prompts`** then a fan-out of `Agent`
   invocations by the orchestrator (one Agent per node, parallel). Each agent
   writes its verdict to `validation_verdicts/node_<id>.json`. Then
   `validate_graph.py --mode collect --apply-patches` merges.

Either way, the script never lets an LLM see more than one node + neighbors at
a time.
